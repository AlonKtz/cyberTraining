Lab 1 — SQL Injection

SQL Injection

An attacker puts database commands inside form fields. The server blindly stitches them into a query and executes whatever they wrote.

📚 How it works When a login query is built like:
"SELECT * FROM users WHERE username = '" + username + "' AND password = '" + password + "'"

…an attacker can type ' OR '1'='1 as the password and the resulting SQL becomes always-true, bypassing authentication entirely.
⚠ Vulnerable login This builds its SQL query using string concatenation. The database executes whatever you inject.

Login Form VULNERABLE

Try these as the password:

' OR '1'='1
' OR 1=1--
' OR 'x'='x

Or dump all users — username: ' OR 1=1--

Code (vulnerable)

// ❌ DANGEROUS — never do this
const query =
  "SELECT * FROM users " +
  "WHERE username = '" + username + "'" +
  " AND password = '" + password + "'"

db.execute(query)

What happens with a payload

username=admin · password=' OR '1'='1

SELECT * FROM users
WHERE username = 'admin'
  AND password = '' OR '1'='1'
--  ^^^ always true ^^^
✅ Secure login Uses a parameterized query. The ? placeholder is always treated as data — never as SQL code.

Login Form SECURE

Hint: try ' OR '1'='1 — it will fail.

Code (secure)

// ✅ Parameterized query
const user = db.prepare(
  'SELECT * FROM users WHERE username = ?'
).get(username)

if (user && user.password === password) {
  // logged in
}

Why this is safe

The ? placeholder is passed separately. The driver escapes it as a literal value — injected SQL is never parsed as a command.

📚 Full Explanation

Root cause: The server builds SQL by gluing user input directly into the query string. The database engine has no way to tell what is "data" vs what is "command".


Classic bypass: Typing ' OR '1'='1 as a password closes the quote, adds a condition that is always true, and logs in as any user.


Comment trick: Using -- in a payload comments out the rest of the query. So admin'-- as a username logs in as admin with any password.


Data exfiltration: More advanced payloads use UNION SELECT to read other tables and exfiltrate data.


Fix: Always use parameterized queries (prepared statements). The input is passed as a bound parameter — the driver handles escaping and the database treats it as data, never code.

🏁 Challenge: dump all users

Using the vulnerable login, craft a username payload that returns every row in the users table. Hint: use -- to comment out the AND clause.

Username: ' OR 1=1--   Password: (anything)

Resulting query:
SELECT * FROM users WHERE username = '' OR 1=1-- AND password = '...'

The -- comments out everything after it. OR 1=1 is always true, returning all rows.
