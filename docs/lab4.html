Lab 4 — Password Storage

Storing Passwords Safely

Plain-text passwords in a database mean one breach exposes every account. Hashing converts passwords into an irreversible fingerprint so a stolen database is useless.

How hashing works A hash function transforms any input into a fixed-length string. The same input always produces the same hash, but you cannot reverse a hash to its original value. To verify a login you hash the attempt and compare it to the stored hash.

What an attacker does next

With plain-text: Instantly knows every password. Can log in to every account. Tries each password on Gmail, Twitter, banking sites (password reuse is very common).


With bcrypt hashes: Must brute-force each hash individually. bcrypt is intentionally slow (~100 ms per attempt on modern hardware). A 12-character random password would take billions of years. Weak passwords like 123456 may still be cracked — which is why bcrypt includes a random salt per password, defeating precomputed rainbow tables.

Register PLAIN TEXT

Password stored exactly as entered.

// ❌ Plain text
users.push({ username, password })
// stored: "MyPassword123"

Register BCRYPT

Password hashed with bcrypt (cost 10) before storage.

Note: bcrypt takes ~100 ms intentionally — this delay is the protection.

// ✅ bcrypt hash (cost factor 10)
const hash = await bcrypt.hash(password, 10)
users.push({ username, passwordHash: hash })
// stored: "$2a$10$..."
Pre-seeded accounts (both databases) alice / password1  ·  admin / admin123

Login PLAIN TEXT comparison

// ❌ Direct string comparison
const user = users.find(
  u => u.username === username
    && u.password === password
)

Login bcrypt.compare

// ✅ Hash the attempt, compare
const user = users.find(
  u => u.username === username
)
const ok = await bcrypt.compare(
  password,          // attempt
  user.passwordHash  // stored hash
)

Why plain text is catastrophic

Databases get breached — it happens to large companies regularly. If you store passwords as plain text:

  • Every user's password is immediately readable
  • ~60% of users reuse passwords — attacker tries them on email, banks, social media
  • You face legal liability for the breach

Why bcrypt, not MD5 or SHA-256

MD5 / SHA-256 are fast — designed for checksums. A GPU can compute billions per second, making brute-force trivial.


bcrypt is slow by design — cost factor 10 means 2¹⁰ = 1024 rounds per hash. ~100 ms per attempt. Fast enough for login, devastating for brute-force (≈10 attempts/sec vs billions).


bcrypt includes a salt — a random value mixed into every hash. Two identical passwords produce completely different hashes, defeating rainbow tables.


Alternatives: Argon2id (recommended for new systems), scrypt. All share: slow + salted.

Challenge: anatomy of a bcrypt hash

Register a user in the secure tab, then leak the secure database. Decode the hash: what do the different parts mean?

Example: $2a$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy

$2a$ — bcrypt algorithm version
$10$ — cost factor (2¹⁰ rounds)
next 22 chars — random salt
remaining chars — the actual hash

The salt is stored inside the hash string, so bcrypt.compare() can extract it and rehash the attempt the same way.
