Lab 2 — Cross-Site Scripting

XSS (Cross-Site Scripting)

An attacker injects JavaScript into your site. Other users load the page and the script runs in their browser — stealing cookies, redirecting them, or defacing the page.

How it works If a comment is stored as-is and rendered with innerHTML, any HTML/JS inside it executes. A payload like <img src=x onerror="alert(document.cookie)"> runs the moment the page loads.
Vulnerable comment board Comments are rendered with innerHTML — any HTML or script you post will execute for every visitor.

Post a Comment VULNERABLE

Basic alert:
<script>alert('XSS!')</script>

Image error handler (bypasses many filters):
<img src=x onerror="alert('cookie: '+document.cookie)">

Page defacement:
<script>document.body.style.background='red';document.body.innerHTML='<h1>HACKED</h1>'</script>

Bold tag (harmless but shows HTML executes):
<b style="color:red">I am bold HTML</b>

Code (vulnerable)

// ❌ Stored as raw HTML
comments.push({ author, body })

// ❌ Rendered with innerHTML
div.innerHTML = `
  <div class="meta">${comment.author}</div>
  <div class="body">${comment.body}</div>
`
// Any <script> or event handler executes!

Code (secure)

// ✅ Escape HTML entities before storing
function escapeHtml(str) {
  return str
    .replace(/&/g, '&amp;')
    .replace(/</g, '&lt;')
    .replace(/>/g, '&gt;')
    .replace(/"/g, '&quot;')
    .replace(/'/g, '&#x27;')
}

comments.push({
  author: escapeHtml(author),
  body:   escapeHtml(body)
})

// ✅ Or use textContent — never innerHTML
el.textContent = comment.body

Full Explanation

Root cause: User input is reflected back to the browser without escaping. The browser's HTML parser treats it as markup and executes any script it finds.


Types of XSS:

  • Stored XSS — payload saved to DB, served to every visitor (this lab).
  • Reflected XSS — payload in a URL parameter, echoed in the same response.
  • DOM XSS — JS on the page reads attacker data and writes it to the DOM.

What attackers do with XSS: Steal session cookies (document.cookie), keylog passwords, redirect to phishing pages, deface the page, exfiltrate data silently.


Fixes:

  • Escape HTML entities in all user-supplied output.
  • Use textContent instead of innerHTML where HTML isn't needed.
  • Content Security Policy (CSP) header blocks inline scripts as a second layer.
  • Use DOMPurify when you genuinely need to allow some HTML.

Challenge: cookie theft simulation

Post a payload to the vulnerable board that reads document.cookie and shows it in an alert. Then explain why HttpOnly cookies would mitigate this.

Payload: <img src=x onerror="alert('Stolen: '+document.cookie)">

HttpOnly cookies cannot be read by JavaScript at all — document.cookie won't include them. Even with XSS, the attacker can't steal the session token if it has the HttpOnly flag.
