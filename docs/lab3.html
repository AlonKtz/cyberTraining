Lab 3 — CSRF

Cross-Site Request Forgery

An attacker tricks a logged-in user into unknowingly sending a forged request to your server. The server sees a valid session cookie and obeys.

📚 How it works Browsers automatically attach cookies to every request — even those triggered by a page on a different domain. If a malicious site posts a hidden form to your bank's /transfer endpoint while you're logged in, the bank will process it because the session cookie was sent automatically.

Secure endpoint

// ✅ Validate CSRF token
function transfer(req) {
  const session = getSession(req.cookies)
  const { to, amount, csrfToken } = req.body

  if (session.csrfToken !== csrfToken) {
    throw new Error('403 Forbidden — bad CSRF token')
  }
  // Token valid — process transfer
  deductFrom(session.user, amount)
  creditTo(to, amount)
  session.csrfToken = newToken() // rotate
}

📚 Full Explanation

Root cause: Browsers automatically attach cookies to every request to a domain, regardless of where the request originates. An attacker's page can submit a form to your site and your server can't tell if it came from your UI or theirs.


CSRF token fix: Generate a secret random token per session, embed it in every form as a hidden field. The server checks it on each state-changing request. A cross-site form can never read this token (same-origin policy) so it can't include it.


SameSite cookies: Setting SameSite=Strict on the session cookie tells the browser not to send it on cross-site requests at all — a modern, simpler defence that works alongside tokens.


Origin/Referer check: Reject requests whose Origin header doesn't match your domain. Simple but less robust on its own.

🏁 Challenge

Why can't the attacker just read Alice's CSRF token from the bank's page and include it in the forged form?

The Same-Origin Policy prevents JavaScript on evil.example.com from reading content from bank.example.com. The attacker's page can send requests but can't read the response — so it can never retrieve the token.
